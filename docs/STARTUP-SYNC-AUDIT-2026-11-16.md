- 没有修改配对、令牌、网络策略、供电限制或服务器数据库，没有上传合成词条到生产服务。

## 已确认的问题和源码修复

1. `LearningStore.snapshotOwn()` 原来持有候选查询也使用的类锁，读取历史与本机文件，并对每个拼音文件反复排序合并整个历史。文件数量越多，重复处理越多，后台同步会直接阻塞首键候选。现在历史文件解析、最终合并放到锁外；先汇集再合并一次，仅短暂保护内存快照和单个本机文件读取。
2. `mergeShared()` 原来持有同一个类锁执行整表合并及 `AtomicFile.finishWrite()`。现在共享文件提交使用单独的写锁，生成与写盘完成后才短暂发布内存索引；候选查询可以继续使用上一份已提交索引。并发共享写入仍串行，重载与共享写入使用相同锁序。
3. 手机下载的完整词库分成 500 行一批。过去即使内容完全相同，每批仍重写整张词条表、学习表和索引。现在已覆盖的词条权重、学习次数和时间戳直接跳过；有新增或增大的值仍原子写入。
4. `RimeBridge.prepare()` 原先在引擎初始化前同步查询 Android 系统用户词典；外部 provider 迟缓会拖延整个中文引擎就绪。导入词库仍在初始化线程预载，系统词典查询移到引擎就绪之后，继续复用这一条初始化线程。增加资产、索引、原生引擎及会话阶段的耗时和失败阶段日志，不记录词条或输入。
5. 更新器现在分开保存最近尝试和最近成功，保留升级前已有的成功时间；失败记录导出、网络、校验或保存阶段，以及 TLS、超时等分类，不记录异常原文。系统停止或任务超时不会写成同步成功。共享页显示这些信息。桌面 `status.json` 也记录失败及最近成功时间，避免旧成功文件一直看起来正常。

没有新增轮询、定时器、保活、唤醒锁或常驻写盘线程。现有小时调度与供电策略保持一致。

## 验证

`tests/run_learning_contention_checks.py` 在独立 UID 中生成 12,000 条历史记录、600 个本机学习文件，并对共享文件模拟 800 毫秒慢写盘。基线为 `c26b974` 的六个实际存储源码文件；修复版使用工作区源码。更新器状态检查两轮均使用修复版源码，各报告分别记录哈希。

| 检查 | 基线 | 修复后 |
| --- | --- | --- |
| 两次导出 | 8,627 / 8,714 ms | 352 / 310 ms |
| 导出期间主线程候选查询 | 8,607 / 8,695 ms | 0.22 / 0.09 ms |
| 800 ms 共享写盘期间查询 | 803 ms | 0.13 ms |

由于现有 API 37.1 镜像的 SurfaceFlinger 重复崩溃，性能检查使用稳定的 API 24 x86_64 测试镜像，仅验证 Java 存储与监控逻辑。测试清单降到 API 24；正式应用仍要求 API 32。合成词条直接构造，不以旧系统 ICU 验证正式导入解析器。没有运行正式键盘、原生 Rime 或个人数据库。手机临时独立包安装超时，安装会话已撤销，未执行该包。

## 仍需正式签名环境复测的路径

- `RimeBridge.sync()` 与按键 JNI 共用同步锁，并等待原生维护线程。导出前“键盘隐藏／未组成拼音”的检查存在时序窗口，维护刚开始时重新打开键盘仍可能等待。未通过跳过快照刷新来改变原生学习共享的范围；需要正式包线程跟踪来测量并继续处理这一段。
- 当前预热探针只使用隐私方案；普通方案的首次用户词典加载、初次部署的资产复制与原生完整维护仍需分别计时。保留原有隐私探针，新增阶段日志用于后续定位。
- 实际选词仍同步保存本机累计文件，慢存储上的提交耗时尚未测量。本轮没有把保存改成可能丢失最近选择的异步队列。

真机当前没有本次启动以来的 ANR 记录，退出历史也没有 1.3.8 安装后的键盘崩溃；这些只能说明没有捕获到相应系统记录，不能排除用户观察到的卡顿。现已复现并修复一个足以造成多秒候选阻塞的独立问题，尚不宣称它是每次真机卡顿的唯一原因。
