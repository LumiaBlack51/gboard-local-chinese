# 词库同步恢复与 1.3.9 安装记录

同步于 2026-11-16 晚恢复，PLQ110 已同签名升级键盘和更新器至 1.3.9。2026-11-17 11:00:54 +08:00，Linux 小时任务再次确认成功，客户端收到 38,002 条词条和 24,110 条学习记录；数量会随真实学习继续增长。

## 同步故障与恢复

用户确认服务器 IP 从 `45.76.170.31` 改为 `64.56.71.36`。新地址的 HTTPS 证书通过系统 CA 和 IP 主机名校验，没有关闭 TLS 验证。新服务器留存的是旧版服务及早期词库，缺少当前共享学习表和三台设备的认证摘要，因此仅更新证书或客户端地址不足以恢复。

先备份新服务器原数据库、脚本及 nginx 配置，再升级服务并恢复三台设备的认证摘要。令牌未更换；客户端私有配对只修改 endpoint。恢复上传使用 Linux、手机和 Windows 各自的本机词条与累计选择次数，未将下载的共享总数作为本机次数上传。首次恢复得到 36,828 条词条、24,049 条学习记录，旧缓存的全部 18,479 条学习记录及次数均被覆盖，首次响应的计数与各设备本机计数之和一致。后续真实同步继续补充词条与学习。

并发交换还暴露了网关继承的 3 秒连接超时：socket 激活的串行后端处理第一台设备时，第二台的 TLS 握手可能超时。仅同步路由改为连接 15 秒、读取 30 秒，服务端 CPU 上限从 20% 调至 50%。两台真实客户端同时交换均 HTTP 200，用时 8.014／4.094 秒。其他网关路由及客户端原有供电、小时调度策略保持原样。

三端均完成实际交换。手机正式更新器通过签名保护接口导出、合并后报告成功；1.3.9 的实际 JobScheduler 任务再次成功，收到至少 24,050 条学习记录，独立同步进程退出。桌面 timer 仍启用，Windows 原有插电与登录任务保留。

私有配对、词条和回滚备份不进入源码与 Release。服务端保留迁移前备份，并通过 SQLite 在线备份 API 生成恢复后的快照，完整性检查通过；这些数据备份不作为构建缓存清除。

证据：[服务端恢复](../tests/results/sync-recovery-server-2026-11-16.json)、[并发交换](../tests/results/sync-concurrency-2026-11-16.json)、[手机正式交换](../tests/results/phone-sync-restored-2026-11-16.json)。

## 构建与真机检查

使用独立 Windows 构建目录和原有正式签名密钥生成键盘、更新器；语音与校对使用哈希核验一致的原正式包。全部七个 APK 的签名、版本、16 KiB 对齐及发布约束通过。82 个编译源码哈希与当前 Java/JNI 源码一致；大 APK 通过压缩载荷索引生成差量传回，重建后核验完整 APK SHA-256。

手机采用同签名覆盖安装，未卸载或清除数据。七个实际安装 APK 哈希与发布清单完全一致，键盘首次安装时间、默认输入法、十项增强设置和两个字号值保留。原有 4,140 条本机学习记录的累计次数均未减少。

所有测试按键仅发送到自有、无联网权限且不保存输入的 probe 编辑框：

- 普通输入 `nihao`，观察到“你好”首候选，清除组成串。
- 隐私模式输入 `nihao` 并选择，编辑框实际得到“你好”，该词的本机学习次数未增加。
- 明确切换普通模式，在观察到真实小时同步进程运行时输入 `zhi`，截图确认组成串和候选已显示，再清除组成串。三次 ADB 点按命令分别为 70.83／55.13／35.80 毫秒，包含 ADB 开销，不能作为触摸到显示延迟。
